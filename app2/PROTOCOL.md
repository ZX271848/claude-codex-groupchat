# Coordinator client

## Optional mobile transport

`mobile.py` hosts an opt-in loopback-only companion behind private Tailscale HTTPS inside the desktop process. An authenticated request names an explicit room; it uses `App.sess(rid)` and the same conversation queue as the desktop bridge. It never invokes `Api.switch_room`, changes the desktop route/cursor, or creates a separate worker runtime. Browser cursors and drafts remain in that live page, without persistent browser storage. Only public events are projected into the mobile snapshot. Same-owner Tailscale identity, Secure host-only pairing cookies, session revocation, request limits, Host/Origin checks and the explicit HTTP action allowlist are transport concerns; they do not change routing or collaboration semantics.

The backend binds only `127.0.0.1`. `mobile_transport.py` verifies the private Serve mapping, refuses enabled Funnel configuration, and checks the trusted proxy headers on every request. Funnel requests, other Tailscale users, missing identities and plaintext origins are denied. Local processes remain within the desktop trust boundary. Legacy HTTP pairings are invalidated on migration; changing the Tailscale owner invalidates pairings. No fallback to LAN HTTP exists.

Mobile action IDs are recorded before admission and retained beyond their acceptance window. Retries reuse the same ID and body. User channel records carry `mobile_request_id` as audit metadata so a retry after restart can recognize a recorded message. An unconfirmed admission across restart is never automatically replayed. Receipt means queued or recorded, not proof that a provider completed the work. See [mobile usage and boundaries](../docs/MOBILE.md).

The sole path is: append user chat → explicit recipient or one Opus 5.5 low classification → persistent worker delivery → append public answer/progress or internal work record → UI polling. There are no front discussion sessions, dispatch handshakes or task-association classifiers.

`routing.py` keeps one tool-less, safe-mode Claude process/session per room, using stream-JSON stdin/stdout. The first call receives the existing public chat; later calls append only new public messages to the running process, with image counts rather than file contents. A stable session, system prompt and room-specific cwd preserve the cacheable prefix. CLI process-per-turn resume was tested and missed the conversation cache, so resume is reserved for a client restart. Native `--autocompact 100k` handles context growth; compaction and cache expiration can still require a new cache write. `routing-session.json` records session ID, accepted history cursor and cumulative provider cost; audits record each call's cost delta separately. An uncertain failed call starts a fresh router session on retry, rebuilding public context rather than reusing a half-accepted turn. Worker sessions are unaffected. Client shutdown closes only its own classifier processes.

`prompts/coordinator-memory.md` asks for a JSON recipient (`gpt`, `claude` or `both`) plus optional explicit routing-preference edits. `routing-memory.json` stores those preferences with their source user message; it is supplied every turn and survives native compaction. Ordinary research content is not stored as a routing preference. The classifier also receives current worker busy/idle states: an independent new topic prefers the idle worker, while corrections, status questions and continuations stay with the responsible worker. Explicit mentions and recipient buttons bypass classification. Invalid results leave a retryable message, never silently select a different model. Routing usage (including provider cache usage) goes to `routing-log.jsonl`; the classifier never sees that log, internal worker notes, task registries or collaboration state. The legacy enum-only `coordinator.md` remains compatible with an already-running old client until it is safely restarted.

`conversation.py` owns scheduling on one queue. Only `gpt-work.json` and `claude-work.json` are resumed. Existing front IDs remain archived, unused. Current instructions live in `app2/prompts/work.md`; old app/prompts are not loaded. Claude uses `--system-prompt-snapshot off` on resume so stale front/back instructions are replaced. GPT resumes with the current developer instructions. Each delivery states the current mode and request message IDs.

Normal mode inserts a user message into its selected busy worker at the supported reception boundary. Only that message is inserted; unrelated history remains deferred. An idle selected worker gets its unread history once. Both means GPT first, then Claude with the user message and GPT answer; it does not enable collaboration. Stop/failure in the first response does not silently advance to the second.

The collaboration switch is explicit per room. It enables peer notes to steer a running collaborator, never to wake an idle one. A complete `@Claude`/`@GPT` request or `<collaborate target="…">…</collaborate>` can wake the peer. The reply returns to the requester. Quoted examples and incomplete tags are ordinary text. Turning collaboration off blocks queued peer requests and further broadcasts. Retained notes can still arrive on the next ordinary invocation, as history, not as new instructions. The classifier does not manage these exchanges.

Ordinary working notes stay internal. Explicit `<progress>…</progress>` publishes during the turn; final answers publish at completion. Neither publication alone wakes another model. Peer requests and progress are deduplicated within a turn, including streamed and final versions. Native tools/notes and old chat remain preserved.

Claude stream input can fold an inserted message into the current turn, or queue it for a separate turn; queued messages can also coalesce. Message count therefore cannot predict result count. The transport uses the producer's `queued_turn_count` on each result: positive means publish an intermediate answer and await the next turn; zero means finish. If the producer omits the field, treat the result as turn-complete and publish any subsequent native response as a new turn. Result queue metadata is logged without prompt text. Native background-task notifications can initiate their own turns; their results are published even without a client-originated request, and user insertions during those turns retain their delivery receipts. The client does not synthesize experiment progress or start a second monitor.

Delivery cursors advance only after a transport accepts a request, and inserted message IDs are kept separately so deferred messages are not skipped. `dispatches.json` records pending/failed/completed requests. Unconfirmed work after client restart becomes retryable, not automatically executed. Provider acceptance is not proof the model has acted; retries after ambiguous connection loss can repeat context, never silently claim exactly-once execution.

UI shows current collaboration mode, worker busy/idle state, retryable dispatches and public progress. Status reconciliation clears stale live bubbles. The visible mode changes after the scheduling queue applies it, not optimistically.

Retryable dispatches appear in a separate, initially collapsed historical section, identified by message IDs. A user stop and an uncertain dispatch after client restart are interruptions, not evidence the current connection failed. Provider error details remain in the dispatch log; retry explicitly redelivers the old request and is unnecessary if the user has already resumed it in a new message. A later successful response does not silently mark unrelated interrupted requests as completed.

The user's global instructions (e.g. `~/.codex/AGENTS.md`, `~/.claude/CLAUDE.md`) are never modified by the client. Migrating to this client does not touch any project's own instructions or running work.

Activation requires exiting the old client from its tray menu and opening the existing shortcut again; closing the window only hides it. Do this only after its model work and native monitoring tasks can be stopped/reconnected safely. Do not open two clients on the same room's native sessions. Updating files or refreshing the page cannot replace Python scheduler objects already running. This migration itself does not restart the client or research processes.

## Room members: Gemini (2026-10-16)

A room's `room.json` may list `"members"`; without it the room is the original GPT/Claude pair and behaves exactly as before. A room listing `gemini` gets a third persistent worker: Gemini through the Google Antigravity CLI (`%LOCALAPPDATA%\agy\bin\agy.exe`, sign-in shared with the Antigravity desktop app), driven in its documented headless mode (`--input-format stream-json --output-format stream-json`), one process per room kept between turns, conversation id in `gemini-work.json`, `--dangerously-skip-permissions` (full access, like the other two). Defaults: Gemini 4 Argon, effort high (agy model slugs end in the effort).

agy differs from the other two transports: a message written during a turn runs as a separate next turn (its `queuedMessages: send-immediately` setting is ignored in headless mode, `qa/probe_agy3.py`), there is no interrupt request, and input is text only, so pictures go by path. So `steer()` declines and the coordinator queues the message until the turn ends. Emulated insertion (end the process at a tool boundary, resume the conversation with the message, `qa/probe_agy4.py`) worked in tests but was withdrawn on 2026-10-17: in a real room it cut a reply mid-way and left a cancelled step in the conversation, and agy then reported later turns there as failed ("The stream was interrupted…") although Gemini had written complete answers. A turn reported as failed still publishes the answer it wrote; a status other than that retry notice is shown beneath it; every result's status goes to `routing-log.jsonl`. Stop ends the process; the next turn resumes the conversation by id. Gemini's weekly and 5-hour limits come from `agy -p /usage --output-format json` (no model call). agy has no flag for added instructions: `prompts/gemini.md` plus the user's global philosophy (`~/.codex/AGENTS.md`, `~/.codex/principles/world-model-alignment.md`, verbatim) open Gemini's conversation once. Text between tool steps is the working note; the text after the last tool step is the answer; tool steps go to the controller work record.

Routing in a room with Gemini: `@Gemini` or the Gemini button; `all` (button 全体) means GPT → Claude → Gemini in turn, each reading the answers before it; `both` stays GPT → Claude. The classifier uses `prompts/coordinator-memory-gemini.md` on the room's existing routing session (only its prompt file changes), sees all three busy/idle states, and is told not to move GPT's or Claude's tasks to Gemini just because it is idle. Collaboration requests may target any member of the room; requests to non-members are ignored.

A joining member reads the chat verbatim from its join point (`cursor-lane-<member>-work.json`, `<member>-join.json`), not the whole archive; its first message names `channel.jsonl` for earlier lines. `tools/add_member.py <room> [--from-seq N]` adds a member. 桌面live助手 got Gemini from #2445. Tests: `qa/test_gemini_member.py` (offline), `qa/test_gemini_live.py` (real agy, cheap model, throwaway room).
